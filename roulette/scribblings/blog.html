The BLOG Language🔗

 #lang roulette/example/blog package: roulette

BLOG is a small probabilistic programming language. This implementation supports a subset of BLOG, built on roulette/example/disrupt. Simple BLOG programs should run without modification.

"blog-example.rkt"

#lang roulette/example/blog

 

type Person;

distinct Person Alice, Bob;

 

fixed Boolean AlwaysTrue = true;

fixed Boolean IsAlice(Person p) = p == Alice;

 

random Real prob ~ Categorical({0.1 -> 0.5, 0.9 -> 0.5});

 

random Boolean Smokes(Person p) ~ BooleanDistrib(prob);

 

random Boolean Healthy(Person p) ~

  if Smokes(p) then BooleanDistrib(0.4)

  else BooleanDistrib(0.9);

 

 

random Boolean Infected(Person p) ~ BooleanDistrib(prob);

 

random Boolean ExtraHealthy(Person p) ~

  if (exists Person q Infected(q)) then BooleanDistrib(0.2)

  else BooleanDistrib(0.8);

 

obs Smokes(Alice) = true;

 

query (ExtraHealthy(Alice));

Here are the supported features:

  • Declare types with type and objects with distinct. Indexed declarations such as distinct Person P[3]; create three distinct objects, accessible as P[0], P[1], and P[2]. Indices may be arithmetic expressions or finite random values.

  • The fixed declarations define constants or functions with parameters. The random declarations use ~ for a distribution or = for a deterministic dependency. Repeated calls to a random function with the same arguments reuse the same random value.

  • BooleanDistrib(p) returns a Boolean. Bernoulli(p) returns 1 with probability p and 0 otherwise. UniformInt(lo, hi) gives equal probability to every integer between the bounds, including both endpoints. Categorical accepts a map such as Categorical({0 -> 0.25, 1 -> 0.75}) where the probabilities must sum to one. Distribution parameters and the choice of distribution may depend on finite random values.

  • The arithmetic operators are +, -, *, /, ^, %, and unary + and -. The comparison operators are ==, !=, <, <=, >, and >=. The Boolean operators are !, &, |, and =>. The forall and exists quantifiers range over the objects of a declared type.

  • Conditionals are written as if condition then expression else expression. Case expressions use case value in {key -> result, ...}. Branches may return values or distributions. An omitted else or an unmatched case returns null.

  • Supply evidence with obs expression = expression; and query an expression with query expression;. Queries execute sequentially using preceding observations. query expression1, expression2; requests one joint distribution.

  • Comments use // or non-nesting /* ... */.

1 Declaration order and random-function domains🔗

Random functions are instantiated eagerly: when a declaration is evaluated, its body is evaluated once for every argument tuple formed from the objects currently declared in its parameter types. The resulting table is fixed for that function. Later object declarations do not extend it.

For example, both people below exist before Age is declared:

#lang roulette/example/blog

 

type Person;

distinct Person Alice, Bob;

random Integer Age(Person p) ~ UniformInt(20, 40);

 

query Age(Alice);                    // works

query Age(Bob);                      // works

query Age(Alice) == Age(Alice);       // always true

The declaration creates one random age for Alice and another for Bob. Repeated calls with the same person retrieve that person’s stored choice; calling the function does not draw another age.

In this separate example, Bob is declared too late for Age:

type Person;

distinct Person Alice;

random Integer Age(Person p) ~ UniformInt(20, 40);

distinct Person Bob;

 

query Age(Alice);                    // works

query Age(Bob);                      // runtime error: outside grounded domains

Bob belongs to Person, but the existing function table has no entry for him. A quantifier over Person can see Bob after his declaration; this does not create an Age(Bob) entry. Declare the complete object population before the random function when all of its members need entries:

type Person;

distinct Person Alice;

distinct Person Bob;

random Integer Age(Person p) ~ UniformInt(20, 40);

query Age(Alice), Age(Bob);           // works

For multiple parameters, instantiation covers every ordered argument tuple:

type Person;

distinct Person Alice, Bob;

random Boolean Friends(Person p, Person q) ~ BooleanDistrib(0.5);

This creates entries for Friends(Alice, Alice), Friends(Alice, Bob), Friends(Bob, Alice), and Friends(Bob, Bob). Declaring Charlie afterward creates no additional entries in this table. An empty parameter domain produces no entries.

These rules apply to random declarations using either ~ or =. Types, objects, and parent functions used by the eagerly evaluated body must already be available. A zero-parameter random declaration evaluates its body once and stores a single value. Fixed functions are ordinary functions and do not create a table over the object population when declared.

2 Sequential and joint queries🔗

A program may contain multiple query statements. Each statement requests one result: either a usual single-expression marginal distribution or a joint distribution over comma-separated expressions. Both kinds execute sequentially. Here, "sequential" describes which preceding observations apply; "joint" describes which values are inferred together in one result.

2.1 Usual sequential queries🔗

Each query uses declarations and observations evaluated before its statement. Later observations do not change an earlier result. Running a BLOG module prints every query result in source order:

#lang roulette/example/blog

 

random Integer X ~ UniformInt(0, 1);

query X;             // 0 or 1, each with probability 1/2

obs X = 1;

query X;             // 1 with probability 1

query X + X;         // 2 with probability 1

Queries reuse the same model allocations; they do not redraw random constants or grounded random functions. Declarations remain subject to the existing loading order and grounding rules.

2.2 Multiple separate queries versus one joint query🔗

Consider two expressions sharing one random variable:

random Integer X ~ UniformInt(0, 1);

query X;             // First result:  0 or 1, each with probability 1/2.

query X + X;         // Second result: 0 or 2, each with probability 1/2.

These are two separate marginal distributions. They reuse the same X, but the results do not explicitly list which pairs can occur together. Multiplying their marginal probabilities would incorrectly assume independence: for example, the pair (0, 2) is impossible even though each component appears in its respective marginal.

To request that relationship explicitly, separate the expressions with commas in one joint-query statement:

random Integer X ~ UniformInt(0, 1);

query X, X + X;

// Joint outcomes: (0, 0) and (1, 2), each with probability 1/2.

Each joint outcome is an ordinary Racket list in expression order. Correlations are preserved: (0, 2) and (1, 0) cannot occur in this example. A single-expression query retains its scalar or structured result; it is not wrapped in a singleton tuple. In particular, query [X, X]; queries one BLOG list value, whereas query X, X; produces ordinary Racket tuple keys. List literals and function arguments can themselves contain commas without splitting the outer query expressions.

Use separate queries when only individual distributions are needed. Use a joint query to inspect correlations or probabilities of combinations. Joint queries may have many more outcomes: two independent variables with m and n possible values can produce m * n joint tuples.

Observations also affect subsequent joint queries. For example, obs X = 1; followed by query X, X + X; has only the outcome (1, 2). An observation placed between two separate queries affects only the later query; an observation before a joint query conditions the entire joint tuple. No observation can occur between the comma-separated expressions of one query statement. Empty joint components and trailing commas are syntax errors.

2.3 Collecting results from Racket🔗

The exported blog-run function accepts a source name and an input port, using the same optional-argument convention as blog-parse. Input is raw BLOG text without a #lang line. It executes the model once, returns every query result, and does not print them:

#lang racket/base

(require (only-in roulette/example/blog

                 blog-run blog-query-result-probabilities))

 

(define results

  (blog-run 'example.blog

            (open-input-string

             "random Integer X ~ UniformInt(0, 1);

              query X;

              query X, X + X;

              obs X = 1;

              query X;")))

 

(map blog-query-result-probabilities results)

; A list containing these PMF hashes, in order:

; {0: 1/2, 1: 1/2}

; {(0, 0): 1/2, (1, 2): 1/2}

; {1: 1}

The exported transparent blog-query-result struct has three fields:

  • number: the one-based query position.

  • expressions: the list of parsed expression datums, including one expression for a marginal query and multiple expressions for a joint query.

  • probabilities: a PMF hash mapping outcomes to probabilities.

The generated accessors are blog-query-result-number, blog-query-result-expressions, and blog-query-result-probabilities. Results preserve statement order and duplicate queries. A program with no queries returns an empty list. Each invocation uses a fresh definition scope and observation session. Errors propagate instead of returning a partial collection, and the next invocation starts with fresh observations.

For an existing #lang roulette/example/blog module, ordinary Racket require still loads the module and prints its sequential results; it does not automatically export a result collection. Use blog-run with the raw program body when an embedding application needs structured results.

3 Lists and matrices🔗

Square brackets construct lists. These two expressions are equivalent:

[[1, 2, 3], [4, 5, 6]]

[1, 2, 3; 4, 5, 6]

The semicolon form is shorthand for a list of rows. Lists may be empty, nested, ragged, or contain nonnumeric values. Shorthand rows must be nonempty; write empty rows explicitly, as in [[], []].

A RealMatrix return annotation converts a list to a numeric matrix:

fixed RealMatrix row = [10, 20, 30];

fixed RealMatrix column = [10; 20; 30];

fixed RealMatrix table = [10, 20, 30; 40, 50, 60];

A flat list becomes a row vector, and nested lists become matrix rows. Conversion requires rectangular data with real numeric cells. Boolean cells, mixed rows and scalars, and nesting deeper than two levels are rejected. Existing matrices pass through unchanged. Exact integers and rationals remain exact; the constructor does not coerce every cell to floating point.

The empty list becomes a 0-by-0 matrix. Explicit empty rows retain their dimensions: [[], []] becomes a 2-by-0 matrix. Matrix constructors also accept zero dimensions.

Conversion applies to fixed constants and functions, and to both forms of random declaration, after a distribution draw or deterministic evaluation. Random functions store the converted result once per grounded argument tuple. An unannotated list expression remains a list, so list and matrix equality does not treat identical-looking contents as the same value.

3.1 Indexing and scalar conversion🔗

All indices are exact, zero-based integers. Indexing dispatches on the value:

  • An indexed distinct-object family returns the selected object.

  • A list returns its stored element, which may itself be a list.

  • A matrix with multiple rows and columns returns a row matrix.

  • A row or column vector returns a 1-by-1 matrix.

query [10, 20, 30][1];                // scalar 20

query [[10, 20], [30, 40]][1];        // list [30, 40]

query [[10, 20], [30, 40]][1][0];     // scalar 30

 

fixed RealMatrix m = [10, 20, 30; 40, 50, 60];

query m[1];                         // matrix [40, 50, 60]

query m[1][2];                      // singleton matrix [60]

query toInt(m[1][2]);                // scalar integer 60

query toReal(m[1][2]);               // scalar real 60.0

query transpose(m)[1];              // matrix [20, 50]

Indexing binds more tightly than arithmetic operators and can follow a literal, function call, parenthesized expression, or another index. For example, (a + b)[i][j] selects a singleton from a matrix sum. Negative, fractional, inexact integer, Boolean, and out-of-bounds indices raise runtime errors. Empty vectors have no valid index; a row of a matrix with multiple empty rows can still be selected as an empty row matrix.

toReal and toInt accept a real or Boolean scalar, or extract the element of a 1-by-1 matrix. Larger or empty matrices are rejected. toReal produces an inexact real; toInt truncates toward zero and produces an exact integer. Booleans convert to 1 or 0. Integer conversion rejects nonfinite numbers.

3.2 Arithmetic and the matrix library🔗

Matrix operands must be matrix values, supplied by RealMatrix declarations or matrix-producing functions. Raw list literals are not automatically converted at an arithmetic operator or library call.

  • a + b and a - b require identical matrix dimensions. Unary + preserves a matrix and unary - negates its cells.

  • a * b performs matrix multiplication, requiring the left column count to equal the right row count. It is not elementwise multiplication.

  • a + s, s + a, a - s, and s - a apply real scalar addition/subtraction to every matrix cell, preserving the shape. In particular, s - a computes s - cell for each cell; adding a scalar does not mean adding a scaled identity matrix.

  • s * a and a * s scale a matrix by a real scalar. a / s divides each cell by a nonzero scalar. Matrix divisors remain unsupported.

  • eye(n), zeros(rows, columns), and ones(rows, columns) construct identity, zero-filled, and one-filled matrices. Dimensions must be nonnegative exact integers.

  • diag(column) creates a diagonal matrix from a column vector. repmat(m, rows, columns) tiles a complete matrix vertically and horizontally using nonnegative exact integer repetition counts.

  • hstack(...) joins matrices with matching row counts. vstack(...) joins matrices with matching column counts. Both require at least one argument and treat real scalars as 1-by-1 matrices, allowing compatible mixtures of scalars and matrices.

  • sum(m) returns the column sums as a row matrix. trace(m) returns the diagonal sum of a square matrix.

  • abs(m) and exp(m) apply elementwise and also accept real scalar inputs.

  • det(m) and inv(m) require square matrices with finite real entries. A singular matrix has determinant zero; its inverse raises an error. The 0-by-0 matrix has determinant 1, trace 0, and an empty inverse.

fixed RealMatrix a = [1, 2; 3, 4];

query a + 10;                       // [11, 12; 13, 14]

query 10 - a;                       // [9, 8; 7, 6]

query a * a;                        // [7, 10; 15, 22]

query sum(a);                       // row matrix [4, 6]

query inv(a) * a == eye(2);          // true with these exact inputs

Inexact arithmetic has ordinary floating-point rounding. Use numerical tolerances when comparing floating-point results from outside BLOG; exact matrix equality is appropriate for the exact example above.

3.3 Random indices, entries, and dimensions🔗

Finite random values may determine indices, matrix entries, and dimensions. Repeated references preserve the same underlying random choices:

random Integer i ~ UniformInt(0, 1);

random RealMatrix a = [i, 10; 20, i];

query toInt(a[i][i]) == i;           // always true

Bounds and dimension checks validate correlated alternatives together. For example, the two reachable shape/index combinations below are both valid:

random Integer i ~ UniformInt(0, 1);

random RealMatrix a =

  if i == 0 then [7] else [10, 20; 30, 40];

query toInt(a[i][0]);                // 7 or 30, each with probability 1/2

Validation skips alternatives whose guards simplify to false under the current execution assumptions. It does not invoke an SMT solver to establish arbitrary unreachability. Invalid alternatives retained by the checks raise errors; they are not silently dropped from the distribution.

Routine arithmetic retains symbolic cells. Determinant and inverse enumerate finite concrete matrix alternatives before pivoted Gaussian elimination; these operations can be expensive with many independent random entries.

4 Current limitations🔗

  • Object populations are fixed and finite. Number statements for unknown populations and origin functions are not supported. Random-function arguments must range over declared object types. Built-in domains such as Integer are not supported as random-function argument domains.

  • Random functions are eagerly instantiated over the objects declared so far. Objects and parent random functions must precede their dependents. Objects declared later are not added to an existing random function’s domain. RealMatrix return annotations are checked and converted; other type annotations are not fully checked.

  • Sets and set comprehensions, higher-dimensional numeric arrays, strings, characters, and timestep literals are not supported. Numeric matrices use RealMatrix; no separate IntegerMatrix type is provided. Distributions other than the four listed above are not provided. Multivariate Gaussian sampling is not implemented. Matrix-valued categorical distributions support finite vector outcomes; matrix support does not provide continuous Gaussian distributions.
